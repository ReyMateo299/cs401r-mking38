## Why the existing workflow is insufficient

The guide's workflow combines `terraform fmt`/`validate`, file-presence checks, a narrow grep near `deduplicate`, optional live AWS verification, and manual review. It is useful evidence gathering, but it does **not** programmatically check all rubric items or produce a 100-point score.

- `verify-lab2.sh` requires a deployed stack and AWS credentials, while teardown is required. Running it after compliant teardown creates expected false failures. The grader will never execute it; submitted logs and code must be usable offline.
- The representative script checks existence/count for several resources but does not verify NAT placement, route, trust principals, all IAM boundaries, lifecycle rule content, crawler schema/status, Glue VPC connection, or all 16 feature names and types. Some account queries select the first available resource rather than a student-specific one.
- Its data checks are helpful but incomplete: they do not check median rather than mean, `order_value` nulls, ID trimming, date-format behavior, deterministic tie-break, category diversity bound, basket denominator, or label derivation. The guide itself warns that pre-2026-09-23 copies printed data-quality FAIL lines without adding them to the summary count. Always inspect individual FAIL lines, not only the summary.
- The script checks `terraform fmt` but not `terraform validate`; it checks contract headings but not content, and only checks diagram presence. It cannot score Tasks 4 and 5 in full or apply the teardown cap reliably.
- The representative script says a `String` `event_time` causes silent drops, but the TA guide's corrected note says `PutRecord` fails the job with a validation error. The pipeline should follow the corrected note and report the source/evidence conflict.
- A grep for `def deduplicate` misses equivalent code organization and cannot prove output grain. Source analysis and data assertions must both be evidence, with manual review for ambiguity.

## Proposed pipeline architecture

1. **One-submission CLI:** accept an explicit submission path and student ID; refuse the aggregate `grading/lab2/` parent and refuse implicit glob/batch traversal. Resolve paths, keep input read-only, ignore generated/vendor/state directories, and inventory Python, Terraform, shell, Markdown, JSON, logs and diagrams.
2. **Collectors:** load source/evidence with bounded file sizes and stable line references. Record submission tag/date when safely available for dated rubric exceptions. Read the default branch separately for the post-tag teardown log. Do not run submitted shell scripts, Terraform apply/destroy, Glue jobs, student Python, AWS CLI, or live policy simulations as part of grading.
3. **Analyzers:** use Python `ast`/`compile` for syntax and structural signals; an HCL parser for Terraform resource/attribute structure; Python `json` for JSON policy/evidence; `bash -n` (and optional ShellCheck) for shell syntax; document/log parsers for evidence. `terraform fmt -check` is deterministic. `terraform validate` is conditional on locally available provider plugins and must run with no cloud credentials or backend initialization; otherwise use committed validation evidence and report it as unverified. Optional `flake8` and `tflint` are diagnostic only: neither can award semantic rubric points or substitute for HCL/AST checks. The current environment has `terraform` and Python 3, but not `tflint` or `flake8` on `PATH`.
4. **Evidence model:** every result stores rubric ID, max points, observed fact, file/line, method (`static`, `committed output`, `manual`), confidence and status (`pass`, `fail`, `needs review`, `unavailable`). A missing log is not proof of a failed AWS job. Disagreements between source and logs are flagged, not silently resolved.
5. **Scoring:** encode the handout-first rules below and compatible guide row weights/deductions. A TA review input records judgments for semantic/data/document items, exceptions, and potential secrets. Generate `grades/<student_id>.md` with item scores, deductions, reasons, evidence, Task 1 cap, any confirmed-secret override, total /100, and unresolved items. A **final** total is emitted only after all score-bearing items and the teardown gate are resolved; before that, label the number provisional. This prevents unsupported zeros or passes from being presented as a final grade.
6. **Verification:** in Phase 3, test parser behavior against small synthetic fixtures and compare rubric totals; in Phase 4, run the CLI on **exactly one** explicit student directory, inspect the resulting document, and stop for TA review. Batch traversal belongs exclusively to Phase 5 after approval.
